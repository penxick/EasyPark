# EasyPark CV — этап 19

FastAPI с готовой COCO-моделью YOLO11n. Выполняется только inference на CPU.
Обучение, датасеты и изменение статусов парковки не выполняются.

## Запуск

Из корня проекта:

```powershell
docker compose up -d --build cv-service
```

Docker использует Python 3.11, PyTorch 2.8.0 CPU и Ultralytics 8.3.236.
Первая сборка скачивает зависимости и веса официального release v8.3.0.
`download_model.py` проверяет SHA-256 перед сохранением в `/app/weights/yolo11n.pt`.
Запуск контейнера и обработка изображений не требуют скачивания весов.
Модель загружается один раз и проходит прогрев до готовности.

## API

`GET /health`: 200 и `{"status":"ok","service":"easypark-cv"}` при готовой
модели; 503, если инициализация модели не удалась. Сервис публикуется только
на локальном интерфейсе `127.0.0.1:8000` согласно Compose.

`POST /detect`: тело запроса — бинарное содержимое JPEG или PNG,
Content-Type — `image/jpeg` или `image/png`. URL, путь файла, JSON и multipart
не принимаются. Лимит — 5 MiB и 12 миллионов пикселей; чтение тела — до 10 секунд.
Ответ соответствует ТЗ:

```json
{"vehicles":[{"type":"bus","confidence":0.9,"bbox":{"x1":10,"y1":20,"x2":300,"y2":400}}]}
```

Координаты — пиксели декодированного изображения с учётом EXIF-ориентации.
Порог confidence 0,25; максимум 100 детекций; размер входа модели 640.
На этом этапе возвращаются поддерживаемые COCO-классы car, motorcycle, bus, truck.
Другие объекты исключаются. При отсутствии транспорта возвращается `vehicles: []`.
Результат не гарантирует обнаружение любого транспорта и не определяет занятость мест.

Ошибки: 400 — пустое/повреждённое изображение; 408 — таймаут загрузки;
413 — превышение лимитов; 415 — неверный Content-Type; 429 — детектор занят
(Retry-After: 1); 503 — модель недоступна или ошибка inference.
Одновременно обрабатывается один запрос, очередь не накапливается.
CPU inference выполняется в рабочем потоке; health остаётся доступным.
Входные изображения и результаты не сохраняются сервисом на диск.

## Проверки

Из `cv-service` после сборки основного образа:

```powershell
docker build -f Dockerfile.test -t easypark-cv-test .
docker run --rm easypark-cv-test
docker run --rm easypark-cv-test ruff check app tests download_model.py
docker run --rm easypark-cv-test python -m pip check
```

Тесты включают реальный inference на стандартном `bus.jpg`, поставляемом
пакетом Ultralytics. Это проверка подключения модели, не датасет и не обучение.
`requirements.txt` фиксирует весь runtime-набор Python 3.11/Linux CPU;
`requirements-dev.txt` подключает его и тестовые инструменты. Рекомендуется Docker:
установленный на хосте Python 3.14 не является проверенной средой этой сборки.

## Собственная модель (этап 19)

1. Положите совместимые веса Ultralytics YOLO для **детекции** в
   `D:\EasyPark\cv-service\models\best.pt`.
2. В корневом `.env` задайте `MODEL_PATH=/app/models/best.pt`.
3. Выполните `docker compose up -d --force-recreate cv-service`.
4. Проверьте `/health` и отправьте изображение через CLI этапа 18.

Compose подключает каталог models только для чтения. Веса не включаются в Git
или runtime-образ. Используйте доверенный файл весов: .pt загружается библиотекой
модели. Совместимость конкретной пользовательской модели проверяется при загрузке
и прогреве; классификационные модели не поддерживаются.

По умолчанию используется `/app/weights/yolo11n.pt`. Для возврата к нему удалите
MODEL_PATH из `.env` либо восстановите это значение и пересоздайте контейнер.
MODEL_PATH в Compose — путь внутри Linux-контейнера, не путь Windows.
При запуске Python напрямую относительные пути отсчитываются от cv-service,
абсолютные пути также допустимы. URL и несуществующие файлы не скачиваются.
Повреждённые/несовместимые веса приводят к 503 readiness без скрытого переключения
на исходную модель. Настроенные классы сопоставляются с метками выбранной модели.
Файл best.pt не поставляется и обучение не выполняется.

## Отправка тестового изображения (этап 18)

После запуска CV-контейнера выполните из корня проекта:

```powershell
python cv-service/tools/detect_image.py "D:\Pictures\parking.jpg"
```

CLI использует только стандартную библиотеку Python, устанавливать PyTorch на
хост не требуется. Передайте существующий JPEG или PNG до 5 МиБ. Изображение
передаётся бинарным телом в `http://127.0.0.1:8000/detect`; тип определяется по
сигнатуре файла, содержимое проверяет сервер. Для другого адреса используйте
`--url http://127.0.0.1:8000/detect`. Таймаут запроса — 60 секунд.

При успехе stdout содержит JSON с `vehicles`, код завершения — 0. При ошибке
файла, соединения или HTTP CLI пишет сообщение в stderr и завершается с кодом 1.
Пустой список vehicles является успешным результатом. Автоматических повторов нет.
Для сохранения ответа средствами PowerShell:

```powershell
python cv-service/tools/detect_image.py "D:\Pictures\parking.jpg" | Set-Content -Encoding utf8 "detection.json"
```

Проверяйте `$LASTEXITCODE`: при ошибке успешный JSON не выводится.

## Библиотека транспорта (этап 17)

`app/vehicle_classes.json` содержит список разрешённых названий: car, SUV,
crossover, pickup, van, minivan, truck, bus, minibus, motorcycle, scooter.
Для изменения списка отредактируйте этот JSON и пересоберите CV-контейнер.
Конфигурация читается один раз при старте; новые зависимости не требуются.

Названия сопоставляются с метками загруженной модели без учёта регистра и крайних
пробелов; числовые ID берутся из модели. API возвращает написание из конфигурации.
Подклассы не угадываются: car не преобразуется в SUV, а motorcycle — в scooter.
Текущая модель поддерживает только car, motorcycle, bus, truck из этого списка.

Отсутствующие у модели классы пропускаются. Если пересечение пусто (включая пустой
список конфигурации), модель всё равно загружается и прогревается, health отвечает
200, а корректное изображение даёт `{"vehicles":[]}` без повторного inference.
Валидация входных изображений сохраняется. Некорректный JSON, нестроковые/пустые
названия и дубликаты — ошибки конфигурации: readiness будет 503, как при остальных
ошибках инициализации. Это отличается от допустимого отсутствия классов в модели.
