# Этап 12 — Reservation Backend

Выполнен только этап 12. Этап 13 (Reservation Flutter) не начат.

## Контракт API

Все три endpoints требуют `Authorization: Bearer <JWT>` и возвращают
`Cache-Control: no-store`. Пользователь определяется из проверенного JWT и БД.

`POST /api/reservations` принимает только:

```json
{ "parkingSpaceId": 1, "durationMinutes": 60 }
```

`parkingSpaceId` — положительное целое ID; `durationMinutes` — 30, 60, 120 или 180.
Начало — текущее серверное время, окончание — начало плюс длительность.
Стоимость фиксируется по тарифу парковки на момент создания: расчёт в копейках,
округление половины копейки вверх. Клиент не может передать userId, цену, статус
или собственное время. Для MVP успешная бронь сразу ACTIVE; платёжного этапа нет.
Ответ 201 содержит поля Reservation: id, userId, parkingSpaceId, startTime,
endTime, status, totalPrice, createdAt, updatedAt. Даты сериализуются в ISO UTC,
стоимость — JSON number в рублях. Пример: 30 минут при 120,51 ₽/час = 60,26 ₽.

`GET /api/reservations/me` возвращает массив только собственных броней,
включая завершённые и отменённые, от новых к старым. Пустой результат — `[]`.
Поля пользователей и их пароли в ответ не включаются.

`PATCH /api/reservations/:id/cancel` отменяет собственную ACTIVE/PENDING бронь
и возвращает её со статусом CANCELLED (200). Повторная отмена CANCELLED
идемпотентна. Чужой или отсутствующий ID возвращает одинаковый 404.
Завершённую/истёкшую бронь отменить нельзя — 409.

Ошибки: 400 — неверные/лишние поля или ID; 401 — нет действующей сессии;
404 — нет места/собственной брони; 409 — место недоступно либо отмена невозможна.

## Транзакции и данные

Добавлены сущность и таблица reservations, внешние ключи на users и parking_spaces
с ON DELETE RESTRICT, проверки статуса, конечного корректного интервала времени
и неотрицательной стоимости, индексы для владельца и истечения срока.
Поддерживаются все статусы ТЗ: PENDING, ACTIVE, COMPLETED, CANCELLED, EXPIRED.

Перед созданием транзакция блокирует строку parking_spaces через SELECT FOR UPDATE,
повторно проверяет FREE, physicalOccupied=false и отсутствие активной брони.
Сохранение Reservation и перевод места в RESERVED выполняются атомарно.
Частичный уникальный индекс UQ_reservations_live_space допускает только одну
PENDING/ACTIVE запись на место даже при записи в обход сервиса. В MVP будущие
интервалы не бронируются: резерв начинается сразу, поэтому ограничение действует
на всё место, а не только на пересекающиеся интервалы.

Отмена и завершение используют тот же порядок блокировок: сначала место,
затем изменение брони. Место освобождается только если его статус RESERVED
и нет другой PENDING/ACTIVE брони. При physicalOccupied=true оно становится
OCCUPIED, иначе FREE. UNAVAILABLE и OCCUPIED не перезаписываются отменой.
Существующие счётчики парковок автоматически отражают изменения статуса.

## Завершение срока

При достижении endTime ACTIVE становится COMPLETED, PENDING — EXPIRED.
Проверка выполняется перед созданием и отменой, при чтении собственных истёкших
броней, а также фоновым обработчиком каждые 30 секунд (до 100 записей за проход).
Это не даёт брони бессрочно блокировать место. После перезапуска сохранённые
истёкшие записи подхватываются следующим проходом. Обработчик безопасен при
нескольких экземплярах backend благодаря тем же блокировкам и повторной проверке.
Ошибка прохода журналируется без приватных данных, следующий проход повторяет попытку.
При остановке приложения таймер закрывается и текущая работа ожидается.

Фоновая проверка имеет задержку до следующего прохода; при большом накопленном
списке может потребоваться несколько проходов. Бронирование конкретного места
проверяет его срок сразу, независимо от фоновой очереди. PENDING сохранён для
контракта ТЗ; текущий публичный POST создаёт только ACTIVE.
