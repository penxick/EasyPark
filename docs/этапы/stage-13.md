# Этап 13 — Reservation Flutter

Реализованы выбор места, длительности, подтверждение, результат и отмена.
Этап 14 (категории истории) не начат.

## Пользовательский сценарий

После выбора свободного места на схеме появляется кнопка «Забронировать».
Она открывает `/parking/:id/book/:spaceId`: экран повторно получает место и тариф,
показывает название парковки, код места и варианты 30 минут, 1, 2, 3 часа.
До подтверждения показана предварительная стоимость с округлением до копейки.
POST передаёт только parkingSpaceId и durationMinutes; время, статус и итоговая
стоимость берутся из ответа сервера. Даты отображаются в часовом поясе устройства.

Во время создания кнопка блокируется, повторное нажатие не отправляет запрос,
обычный возврат назад временно запрещён. Экран результата показывает статус,
время начала/окончания и стоимость. Отмена требует отдельного подтверждения;
после успешного PATCH интерфейс показывает «Бронирование отменено».
Возврат на схему обновляет статусы мест.

Вкладка «Бронирования» загружает текущие ACTIVE/PENDING брони через GET /me,
показывает название парковки и код места и позволяет отменить бронь после
повторного открытия приложения. Есть ручное обновление, обновление при возвращении
к вкладке и возобновлении приложения, загрузка, пустой список и повтор после ошибки.
Категории активных/завершённых/отменённых и экран истории не добавлялись.
После отмены карточка показывает подтверждённый статус; при обновлении она уходит
из списка активных.

## Ошибки и сохранность состояния

- Место, которое уже недоступно при открытии, нельзя отправить на бронирование.
- При 409/404 создания показано предложение вернуться к схеме; повтор блокируется.
- 401 использует существующий механизм завершения сессии и перехода на вход.
- После сетевого/серверного сбоя или некорректного успешного ответа POST результат
  считается неопределённым. «Проверить бронирования» читает GET /me: найденная активная
  бронь этого места показывается пользователю, иначе снова доступно подтверждение.
  Автоматического повторного POST нет. Защита от дублей в БД остаётся на сервере.
- Ошибка отмены не отображается как успех; повторная отмена разрешена и идемпотентна
  на backend. Повторные диалоги подтверждения и запросы во время ожидания блокируются.
- Смена URL места создаёт новое состояние формы, старый выбор не переиспользуется.
- Модель проверяет ID, статус, даты/порядок интервала, конечную неотрицательную цену;
  repository сверяет ID места/брони в ответах и уникальность списка.

## Figma и границы

Изучен BookingDialog.tsx из защищённого экспорта: использованы голубой блок места,
выбор длительности, синие акценты, карточки и структура подтверждения.
Вместо web-диалога используется прокручиваемый Flutter-экран для мобильной ширины
и увеличенного шрифта. Длительности 1–6 часов и способы оплаты из Figma заменены
требованиями ТЗ: 30/60/120/180 минут, без имитации или подключения платежей.
React/TSX и web-зависимости не переносились.

API этапа 12 не содержит названия парковки и кода места в Reservation.
Текущий клиент дополняет активные брони данными существующих endpoints парковок
и мест. Это приемлемо для MVP с тремя парковками; для большого каталога стоит
добавить серверную проекцию данных. Если соответствие не найдено, карточка
сохраняет доступ к отмене и показывает числовой ID места.
