# Техническое задание на разработку EasyPark

## 1. Общая информация

### 1.1. Название проекта

**EasyPark**

### 1.2. Назначение системы

EasyPark — мобильное приложение для поиска парковок, просмотра свободных парковочных мест, выбора конкретного места и его бронирования.

Дополнительно система должна предусматривать отдельный модуль компьютерного зрения, который в дальнейшем сможет определять наличие транспортного средства на парковочном месте.

Обучение собственной нейронной сети в рамках данного технического задания **не выполняется**.

---

## 2. Основная идея приложения

Пользователь открывает EasyPark и видит карту города с парковками.

Для каждой парковки отображаются:

- название;
- адрес;
- расположение на карте;
- стоимость парковки;
- общее количество парковочных мест;
- количество свободных мест.

После выбора парковки пользователь может открыть её схему и увидеть конкретные парковочные места.

Каждое место имеет один из статусов:

- `FREE`
- `OCCUPIED`
- `RESERVED`
- `UNAVAILABLE`

Пользователь может выбрать свободное место и забронировать его.

---

## 21. Статусы парковочного места

Использовать:

- `FREE`
- `OCCUPIED`
- `RESERVED`
- `UNAVAILABLE`

Где:

- `FREE` — место свободно;
- `OCCUPIED` — на месте физически находится автомобиль;
- `RESERVED` — место забронировано;
- `UNAVAILABLE` — место временно недоступно.

```text
C01   C02   C03   C04
```

Каждое парковочное место является отдельным интерактивным элементом.

Статус места должен быть визуально понятен.

## 26. Создание бронирования

Пользователь:

1. выбирает парковку;
2. выбирает место;
3. выбирает длительность;
4. подтверждает бронирование.

Для MVP предоставить фиксированные варианты:

- 30 минут
- 1 час
- 2 часа
- 3 часа

После создания бронирования место становится недоступным для бронирования другими пользователями.

---

## 27. Проверка бронирования

Backend обязан перед созданием брони повторно проверить место.

Запрещено создавать бронь, если место:

- `OCCUPIED`
- `RESERVED`
- `UNAVAILABLE`

Проверка только на стороне Flutter недостаточна.

---

## 28. Защита от двойного бронирования

Если два пользователя одновременно пытаются забронировать одно место, успешно должна создаться только одна бронь.

Проверка должна выполняться на уровне backend и БД.

---

## 29. Отмена бронирования

Архитектура должна позволять работать с распространёнными типами транспортных средств.

```text

```


Для пользователя итоговый статус:

```text

```

Если:


```text

```

Бронирование и физическое наличие машины не должны храниться как одно и то же состояние.

## 58. Критерий готовности CV-модуля

CV-service считается готовым для первого этапа, если:

1. сервис запускается отдельно;
2. `GET /health` отвечает успешно;
3. можно передать изображение;
4. предобученная модель запускает inference;
5. сервис находит транспорт;
6. возвращает тип транспорта;
7. возвращает confidence;
8. возвращает bounding box;
9. модель можно заменить через `MODEL_PATH`;
10. для замены модели не требуется изменять backend и Flutter.

## 60. Порядок разработки

```text
Flutter + Backend + PostgreSQL
            ↓
        Авторизация
            ↓
          Parking
            ↓
      ParkingSpace
            ↓
        Reservation
            ↓
        Полный MVP
            ↓
        CV-service
            ↓
Предобученная модель транспорта
            ↓
Позднее — собственный best.pt
```

Главная задача — сначала получить полностью рабочее приложение EasyPark.

Модуль компьютерного зрения не должен блокировать разработку основного приложения.
