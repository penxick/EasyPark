# A2 — Системный ADMIN и backend-авторизация

Дата: 7 октября 2026 года. Этап завершён; A3 не начат.

## Реализация

Использована существующая таблица users и роль ADMIN. Новая миграция добавляет
nullable login с уникальным индексом и проверкой формата. Существующие USER,
email, пароли и бронирования сохраняются. synchronize остаётся выключенным.

Backend перед открытием HTTP вызывает AdminBootstrapService после применения
миграций. Docker уже запускает мигратор перед main. Для запуска без Docker нужно
сначала выполнить `npm run build` и `npm run migration:run`, затем `npm start`.
Сам мигратор не создаёт администратора до готовности таблиц.

ADMIN_LOGIN и ADMIN_PASSWORD обязательны. Логин нормализуется в нижний регистр,
содержит 1–64 ASCII символа (буквы, цифры, точка, дефис, подчёркивание), начинается
с буквы. Пароль — 12–128 символов, не placeholder; пробелы пароля не обрезаются.
Заданные пользователем данные внесены только в локальный игнорируемый `.env`.
В `.env.example` оставлены `ADMIN_LOGIN=admin`, `ADMIN_PASSWORD=change_me`.
На другом компьютере необходимо задать пароль самостоятельно до запуска.

Служебный email — `admin@easypark.invalid`, поскольку существующая сущность и
Flutter-модель требуют email. Это технический адрес, не почтовый ящик.
Обычная регистрация запрещает домен easypark.invalid и не принимает login,
role или passwordHash. Попытка зарегистрировать email `admin` также невалидна.
Имя пользователя не является логином и не даёт прав.

Создание выполняется транзакционно с PostgreSQL advisory lock. Повторные и
конкурентные запуски не создают дубликаты. Пароль хранится только как scrypt-хеш
через существующий PasswordService. Изменение ADMIN_PASSWORD в env не сбрасывает
пароль уже созданного администратора. Конфликт служебного email/логина/роли
останавливает запуск, не превращая существующего USER в ADMIN. Смена ADMIN_LOGIN
после создания аккаунта также требует отдельной осознанной миграции аккаунта.

## Контракт авторизации и защита

`POST /api/auth/login` принимает ровно один идентификатор:

- `{ "login": "admin", "password": "..." }`;
- `{ "login": "user@example.com", "password": "..." }`;
- прежний `{ "email": "user@example.com", "password": "..." }` сохранён.

Оба идентификатора одновременно, отсутствие идентификатора, null и пустая строка
отклоняются. Регистрация выделена в независимый DTO и по-прежнему требует email.
Ответ содержит прежний безопасный user с role и JWT, без passwordHash.

Экспортирован RoleGuard: использовать `@UseGuards(JwtAuthGuard, RoleGuard)` на
будущих admin-контроллерах. JwtAuthGuard читает актуальную роль из PostgreSQL;
RoleGuard разрешает только ADMIN. Отзыв роли действует сразу для старого JWT.

**В A2 нет производственного admin CRUD endpoint.** Цепочка guard проверена на
тестовом Nest HTTP-контроллере, который не включён в AppModule. Реальные admin
endpoints появятся начиная с A3 и должны использовать эту цепочку. Flutter не
изменён: вход по логину, role redirect и защищённые маршруты запланированы на A7.
Таким образом, вход admin уже работает через API, но ещё не через текущую форму
Flutter, которая проверяет email.

## Проверки

- Nest build, ESLint и Prettier проходят.
- 45 backend-тестов прошли: 12 базовых и 33 интеграционных, без пропусков.
- Проверены миграция up/down в отдельной схеме, соответствие entity/БД,
  конкурентное создание ADMIN, сохранение хеша при повторном bootstrap,
  отказ повышения USER при конфликте, вход по логину/email, неверный пароль,
  резервирование аккаунта и запрет role/login/passwordHash в регистрации.
- Реальный HTTP guard chain: без JWT — 401, USER — 403, ADMIN — 200;
  после отзыва ADMIN — 403, после удаления пользователя — 401.
- Прежние проверки регистрации, JWT, парковок, мест и бронирований прошли.
- Docker backend пересобран и запущен, миграция применена к локальной БД,
  системный аккаунт создан. `node test/docker-admin-smoke.cjs` подтвердил вход
  с данными локального env, отклонение неверного пароля, users/me, хеширование,
  отсутствие хеша в API и идемпотентность bootstrap.
- Flutter и CV не менялись; повторная сборка этих компонентов в A2 не требовалась.

Первый запуск Node test runner в ограниченной среде получил spawn EPERM;
повторный запуск с разрешённым доступом прошёл. Ошибок реализации по результатам
проверок не осталось. Исходные материалы ТЗ/Figma не редактировались.
