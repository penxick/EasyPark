# A6 — Analytics Backend

Дата: 10 октября 2026 года. Аналитика реализована на основе существующей PostgreSQL.
Следующий этап — A7, административная основа Flutter.

## API

Оба метода используют JwtAuthGuard → RoleGuard и Cache-Control: no-store:
без JWT — 401, для USER — 403. Ответы не содержат персональных данных.

- `GET /api/admin/analytics` — общие показатели для Dashboard и аналитики.
- `GET /api/admin/analytics/parkings?page=1&pageSize=20` — показатели по парковкам.

Общий ответ содержит числовые поля:

| Поле                   | Значение                                         |
| ---------------------- | ------------------------------------------------ |
| totalParkings          | Количество парковок                              |
| totalSpaces            | Количество мест                                  |
| freeSpaces             | FREE без physicalOccupied                        |
| occupiedSpaces         | OCCUPIED, а также FREE с physicalOccupied=true   |
| reservedSpaces         | RESERVED                                         |
| unavailableSpaces      | UNAVAILABLE                                      |
| physicalOccupiedSpaces | Все physicalOccupied=true, независимо от статуса |
| totalUsers             | Все пользователи, включая ADMIN                  |
| totalReservations      | Все бронирования, включая завершённые/отменённые |
| activeReservations     | ACTIVE/PENDING с endTime в будущем               |
| occupancyPercent       | Процент загрузки доступных мест                  |

Четыре счётчика статусов не пересекаются и в сумме дают totalSpaces. Отдельный
physicalOccupiedSpaces может пересекаться с RESERVED/UNAVAILABLE, поэтому его
нельзя прибавлять к распределению статусов. FREE с физической занятостью трактуется
согласованно с пользовательскими freeSpaces и Flutter displayStatus.

Формула загрузки:
`100 × (occupiedSpaces + reservedSpaces) / (totalSpaces - unavailableSpaces)`.
При нулевом знаменателе результат 0; округление до двух десятичных знаков.
При создании UI подписывать показатель как загрузку **доступных** мест.
Общий процент вычисляется по суммарным местам, а не усредняется по парковкам.

По парковкам возвращается страница `{items,total,page,pageSize,totalPages}`;
каждый item содержит id, name, все счётчики мест, totalReservations,
activeReservations и occupancyPercent. Сортировка — id ASC. Пустые парковки
включены с нулевыми показателями. Используется общий AdminPageDto: page от 1
до 1000000, pageSize от 1 до 100; значения по умолчанию 1 и 20.

## Расчёты и согласованность

COUNT/FILTER/GROUP BY выполняются PostgreSQL. Общая аналитика — один SQL statement
с единым снимком. Список парковок и его total читаются в REPEATABLE READ транзакции.
Места и бронирования агрегируются отдельно до JOIN: несколько исторических броней
одного места не умножают количество мест. Только финальная формула процента
вычисляется backend из готовых агрегатов. Кэш и захардкоженные показатели отсутствуют.

Бронирования считаются по Reservation, не по RESERVED: в seed встречаются
RESERVED-места без бронирований, и эти значения могут различаться. Истёкшие
ACTIVE/PENDING не входят в activeReservations, как в A4/A5. Счётчики мест отражают
текущий сохранённый статус, согласованный с USER API: до прохода expiry worker
истёкшая бронь может ещё оставлять место RESERVED. GET аналитики не изменяет БД;
после worker следующий запрос покажет новый статус. Физическая занятость читается
из существующего поля и не перезаписывается.

Данные подходят для распределения статусов, сравнения загрузки и числа броней
по парковкам на A12. Выручка/платежи и графики выдуманных исторических измерений
не добавлялись. Новых таблиц, миграций, библиотек или отдельной БД нет.
