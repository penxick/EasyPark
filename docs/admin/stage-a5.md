# A5 — Users и Reservations Backend

Дата: 8 октября 2026 года. Этап завершён; A6 не начат.

## Контракт

Все методы требуют JwtAuthGuard → RoleGuard и возвращают Cache-Control: no-store.
Без JWT — 401, USER — 403. Некорректный ID — 400, отсутствующий объект — 404.

| GET                         | Результат                                                     |
| --------------------------- | ------------------------------------------------------------- |
| /api/admin/users            | Постраничный список всех пользователей, включая ADMIN         |
| /api/admin/users/:id        | Безопасные поля пользователя, счётчики и постраничная история |
| /api/admin/reservations     | Бронирования всех пользователей, категории и пагинация        |
| /api/admin/reservations/:id | Подробности бронирования с пользователем, парковкой и местом  |

Списки и история в карточке принимают page (по умолчанию 1, максимум 1000000)
и pageSize (по умолчанию 20, максимум 100). Разрешены положительные целые числа
в десятичной записи. Дроби, экспоненциальная запись, пустые/повторяющиеся параметры,
неизвестные query-поля и превышение границ отклоняются DTO.

Формат страницы: `{items, total, page, pageSize, totalPages}`. Порядок —
createdAt DESC, id DESC. При выходе за последнюю страницу items пустой,
total сохраняется; у пустого набора totalPages=0. Подсчёт и выборка списка
выполняются в одной REPEATABLE READ транзакции. Пагинация offset-based: между
отдельными запросами страниц добавление новых записей может сдвинуть позиции.

Пользователь: id, name, email, role, createdAt, updatedAt. Карточка дополнительно
содержит reservationCount, activeReservationCount и reservations (страницу истории
только этого пользователя). Счётчики не зависят от выбранной страницы.
Счётчики карточки и её история читаются отдельными запросами; параллельное
создание/отмена брони может отразиться между ними, следующий refresh согласует данные.

Бронирование: id, createdAt, startTime, endTime, status, totalPrice (число),
user `{id,name,email}`, parking `{id,name,address}`, space `{id,code}`.
Список и карточка используют одну явную проекцию с JOIN, без N+1-запросов
за каждой парковкой или пользователем. Возвращаются текущие название/адрес/код
связанных сущностей и сохранённая стоимость брони; исторических снимков адреса нет.

Категории `GET /api/admin/reservations?category=...`:

- all (по умолчанию) — все;
- active — ACTIVE/PENDING с endTime в будущем;
- completed — COMPLETED/EXPIRED, включая истёкшие ACTIVE/PENDING;
- cancelled — CANCELLED.

В административной проекции истёкший ACTIVE показывается как COMPLETED,
истёкший PENDING — как EXPIRED. Это вычисляется на backend одним CASE-выражением
для списка, фильтра и карточки; GET не изменяет таблицы и не запускает массовое
завершение броней. Существующий worker сохраняет переходы в БД. Это исключает
устаревшие «активные» записи между его проходами. activeReservationCount использует
ту же проверку статуса и endTime. USER API и его логика завершения не изменены.

passwordHash не выбирается обычным чтением User и не включается в publicUser.
JOIN-проекция бронирований выбирает только перечисленные поля. JWT, пароли и
служебный login также не возвращаются этими методами.
