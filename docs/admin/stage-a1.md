## User, Auth и системный администратор

Изучены `backend/src/users/`, `backend/src/auth/`, `config/environment.ts`,
`main.ts`, `setup.ts`, `database/migrate.ts` и `database/seed.ts`.

- В User уже есть ADMIN и проверка enum в PostgreSQL. Создавать новую роль не нужно.
- Email обязателен и уникален, нормализуется. Отдельного поля login пока нет.
- `publicUser()` явно перечисляет безопасные поля, включая role; passwordHash
  по умолчанию не выбирается. Этот способ сериализации сохранить в admin API.
- `UsersService.create()` всегда назначает USER. `role` и passwordHash не входят
  в регистрационный DTO, лишние поля отклоняет глобальный ValidationPipe.
- `JwtAuthGuard` проверяет подпись/срок/issuer/audience и читает пользователя из
  БД при каждом запросе. RoleGuard должен использовать request.user.role после
  этого guard, а не роль из клиента или дополнительный доверенный JWT claim.
- LoginDto требует email. **RegisterDto наследуется от LoginDto**: при добавлении
  логина нужно разделить DTO, иначе легко ослабить регистрацию обычного пользователя.
- В `.env.example`, Compose и валидаторе нет ADMIN_LOGIN/ADMIN_PASSWORD.
- Seed сейчас создаёт только демопарковки и места, а не пользователей.
- Приложение и мигратор создают один AppModule. Создание admin нельзя безусловно
  запускать в его bootstrap hook до применения миграций на пустой БД.

Предлагаемая реализация A2:

1. Новая миграция добавляет nullable login с нормализацией и уникальностью,
   не изменяя email/пароли существующих USER. Для системного аккаунта сохранить
   обязательный строковый email, используя зарезервированный служебный адрес
   (например, admin@easypark.invalid); это не реальная почта и не канал восстановления.
2. Вход сохраняет совместимость с существующим телом `{email,password}` и
   получает поддержку идентификатора login; регистрация остаётся строго по email.
   Не принимать одновременно конфликтующие идентификаторы. Пароль не trim-ить.
3. Создание системного ADMIN вызывается после готовности схемы и до приёма HTTP.
   Параллельный запуск защищён транзакцией/уникальностью. Существующий ADMIN
   повторно не создаётся; обычный пользователь при совпадении идентификатора
   не превращается в администратора. Конфликт должен давать понятную ошибку запуска.
4. Использовать текущий PasswordService (scrypt). Реальный начальный пароль из
   задания хранится только в локальном игнорируемом `.env`; в `.env.example`
   будут ADMIN_LOGIN=admin и ADMIN_PASSWORD=change_me. Пароль не помещать в seed,
   Flutter, миграции, отчёты, логи или возвращаемые данные.
5. Резервировать login admin и настроенный системный login; запретить занятие
   служебного email регистрацией. Публичная регистрация не принимает login/role.
6. На admin-контроллерах последовательность JwtAuthGuard → RoleGuard:
   нет JWT — 401, USER — 403, ADMIN — разрешение.

Нельзя подтвердить admin login или 403 на admin API на A1: этих endpoints ещё нет.
Текущее наличие enum ADMIN само по себе не означает реализацию административной части.

## Parking и безопасное удаление

`backend/src/parking/parking.entity.ts` уже содержит name, description, address,
latitude, longitude, pricePerHour, workingHours и timestamps. БД проверяет
диапазоны координат и цену. Поля формы не требуют второй сущности.

`ParkingService.findAll/findOne` и существующие JWT endpoints:

- `GET /api/parkings`;
- `GET /api/parkings/:id`;
- `GET /api/parkings/:parkingId/spaces`.

Они подходят обеим ролям и должны показывать изменения из той же БД. Admin GET
с тем же ответом не добавлять. Запись добавить через `/api/admin/...`; глобальный
префикс /api уже настроен, его нельзя дублировать в декораторах контроллеров.

На A3 нужны trim/проверка непустых обязательных строк, длины 200/500/200,
конечные координаты, цена от 0 до предела numeric(10,2) с максимум двумя знаками,
проверка ID/существования, whitelist PATCH и понятные 400/404/409.

Связи ParkingSpace → Parking и Reservation → ParkingSpace используют RESTRICT.
Политика удаления: место с любой историей бронирований не удалять (409).
Парковку с историей хотя бы одного места тоже не удалять; парковку без истории
можно удалить вместе с её местами в одной транзакции. Проверку и удаление выполнять
с блокировками и обработкой конфликтов внешних ключей, учитывая параллельное
создание брони/места. Не включать CASCADE, уничтожающий историю.

Изменение pricePerHour влияет на новые брони; сохранённый Reservation.totalPrice
не пересчитывается. Изменение имени/адреса/координат отражается в общих чтениях.

## ParkingSpace, бронирование и physicalOccupied

Существующие сущности и сервисы:

- `backend/src/parking-spaces/parking-space.entity.ts` и `parking-spaces.service.ts`;
- `backend/src/reservations/reservation.entity.ts`, `reservations.service.ts`;
- `reservations/reservation-expiry.worker.ts`.

Код уникален по (parkingId, code), длина до 20. x/y — конечные неотрицательные
числа. Polygon сейчас nullable jsonb: БД проверяет лишь массив от трёх элементов.
Для admin DTO дополнительно проверить каждый элемент как пару конечных координат,
ограничить размер ввода и сохранить nullable-семантику. Не угадывать новые координаты
камеры и не пересчитывать polygon при изменении обычных x/y.

Бронь сначала блокирует строку места, завершает истёкшие брони, затем проверяет
FREE, physicalOccupied=false и отсутствие PENDING/ACTIVE. Уникальный частичный
индекс независимо защищает от двойного бронирования. Отмена и expiry используют
тот же порядок блокировок. Admin mutations должны соблюдать его.

На A4:

- Создание места: FREE, physicalOccupied=false, без входного status/role.
- Изменение кода/x/y/polygon не должно перезаписывать physicalOccupied.
- Управлять доступностью отдельно от физической занятости и брони. Выключение
  ставит UNAVAILABLE, не отменяя бронь молча. Включение вычисляет RESERVED при
  живой брони, иначе OCCUPIED при physicalOccupied, иначе FREE, под блокировкой.
- Существующий read-метод дополнить сведением hasActiveReservation через EXISTS;
  статус RESERVED сам по себе не доказывает наличие брони. Персональные сведения
  владельца не добавлять в публичный ответ мест.
- Удаление запрещать при любой истории Reservation; подтверждение — во Flutter.

Особенность демоданных: seed создаёт RESERVED-места без записей Reservation.
Следовательно, число RESERVED и число активных бронирований могут различаться.
Не фабриковать брони для выравнивания показателей и не менять эти данные в аудите.

Flutter `ParkingSpace` содержит physicalOccupied и displayStatus, но пока не
читает polygon. Расширить модель совместимо для редактора A10; существующую
схему `ParkingLayout` и функции цветов/подписей переиспользовать.

## Users, Reservations, Analytics

Сейчас есть только users/me и reservations/me, create/cancel пользовательской
брони. Административного API не найдено. На A5 нужны безопасные проекции list/detail,
JOIN к пользователю, месту и парковке; createdAt уже есть в БД, но отсутствует
в текущей Flutter-модели Reservation. Добавить поле совместимо либо использовать
административную модель деталей поверх общих типов.

Категории сохранить: active = PENDING/ACTIVE, completed = COMPLETED/EXPIRED,
cancelled = CANCELLED. Добавить all. Пагинация на backend: page/pageSize с пределом
размера страницы, стабильный порядок createdAt DESC, id DESC и total. Историю
пользователя также получать порциями; не загружать всех пользователей во Flutter.

Текущий пользовательский `ReservationRepository.history()` обогащает данные через
запрос парковок и их мест. Не переносить этот способ в административный список:
связанные данные должен возвращать backend одним подготовленным контрактом.

На A6 аналитика агрегируется в PostgreSQL (COUNT/FILTER/GROUP BY), не во Flutter.
Один сервис даёт данные для Dashboard и Analytics, отдельный разрез — по парковкам.
Количество пользователей в общем показателе — все зарегистрированные аккаунты;
при необходимости UI отдельно подписывает счётчик USER, чтобы не скрывать ADMIN.

Предлагаемая формула загрузки доступных мест:
`100 × (occupied + reserved) / (total - unavailable)`, при нулевом знаменателе 0.
Её необходимо явно подписать в UI и зафиксировать в контракте A6. physicalOccupied
учитывать согласованно с текущим freeSpaces/displayStatus: FREE с физической
занятостью не считать свободным. Не складывать один слот дважды, отдельно сохранять
показатели статуса и физической занятости. Активные брони считать по Reservation,
а не по числу RESERVED-слотов. Проверить согласованность после expiry.

Не использовать totalPrice как доказательство реального платежа: платёжных
сущностей нет, графики выручки из прототипа не входят в новое минимальное ТЗ.

## Flutter: переиспользование и недостающие части

- `AuthUser` уже принимает USER/ADMIN. AuthController восстанавливает user через
  users/me, хранит JWT в secure storage и корректно обрабатывает logout.
- `auth_form_screen.dart`, AuthValidators и текст ошибок пока требуют email.
  Изменить только режим входа на «Логин / Email»; регистрация остаётся email.
- `core/router/app_router.dart` проверяет только AuthStatus, направляя все роли
  на /map. Добавить role-based landing и запрет /admin для USER, включая глубокие
  ссылки, восстановление сессии и возврат назад. Для ADMIN создавать отдельный shell.
- `ApiClient` уже поддерживает GET/POST/PATCH/DELETE, query, JWT, 401 и 403.
  Второй клиент не нужен. Он не показывает raw body ошибок; сообщения о конфликте
  кода места/истории удаления сопоставлять в admin repository по безопасным кодам.
- Переиспользовать AppTheme/AppTokens, AppCard/AppButton (есть destructive),
  AppTextField, AppTopBar, AppLoadingIndicator/AppErrorView и LoadController.
- `LoadController` подавляет устаревшие результаты; после CRUD обновлять список,
  карточку, карту и аналитику через возврат результата/явное refresh, без перезапуска.
- Новые файлы разместить в features/admin/{data,models,repositories,screens,widgets}.
  Общие модели не копировать ради смены роли.
- Для шести разделов использовать адаптивное административное меню:
  Главная, Парковки, Бронирования, Пользователи, Аналитика, Профиль.

не считать ручное изменение доступности результатом CV.
